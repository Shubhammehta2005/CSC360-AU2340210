## ASCII Tree

An **ASCII tree** is a way of showing a tree structure using only normal text characters in the console, instead of drawing it with graphics.

### Characters we need

To print a tree we mainly use:

```text
|    vertical pipe   -> shows a branch continuing downward
--   horizontal dash -> connects a parent to a child
`    backtick / corner-> shows the last child of a node
+    plus            -> a branch point (child that is not the last)
```

A printed folder tree looks like this:

```text
project
+-- src
|   +-- main
|   `-- test
+-- pom.xml
`-- README.md
```

The `|` keeps the vertical line going for items that still have siblings below them, and the `` ` `` (corner) is used for the last item so the line stops there.

## Console vs GUI for a tree

Printing a tree in the console is often better than drawing it in a GUI because:

- It is **simpler** — no windows, panels or paint code needed.
- It works **everywhere**, including servers with no screen.
- The output is **plain text**, so it can be copied, saved to a file, searched, or sent in a message.
- It is **fast** and uses very little memory.

A GUI drawing is only really needed when we want interaction, like clicking or dragging nodes.

## Benefits of the terminal vs graphics

- Works over a remote connection with low bandwidth.
- Can be **automated** and put into scripts.
- Output can be piped into other tools.
- No dependency on a display or graphics libraries.
- Easier to test in a headless environment (like CI/CD).

## Remote access: SSH and AnyDesk

- **SSH** (Secure Shell) is used to connect to a remote machine over the network and use its **command line**. It does not need a monitor on the remote machine, which is why it is used for servers.
- **AnyDesk** (or similar remote desktop tools) is used when we actually need to see the **graphical desktop** of the remote machine.

So the rule of thumb is: SSH for terminal work on headless machines, remote desktop tools when a real screen view is required.

## Long paths and the 150 character limit

A single line of output should stay within a limit (around 150 characters) so it does not wrap and become hard to read. Deep folder paths can easily go over this.

To handle this, instead of printing the full path on one line:

```text
project/src/main/java/com/example/app/ui/panels/shapes/CirclePanel.java
```

we print the structure using **vertical pipes** and **horizontal dashes**, one level per line:

```text
project
`-- src
    `-- main
        `-- java
            `-- com
                `-- example
                    `-- app
                        `-- ui
                            `-- panels
                                `-- shapes
                                    `-- CirclePanel.java
```

Each level is indented, so the reader can follow the hierarchy without any single line getting too long.

## Custom Splash Screen

A **splash screen** is the small window or image that appears while an application is still loading, before the main window is ready.

A **custom** splash screen is one we design ourselves instead of using a plain default.

### Use case

It is useful when the app takes a few seconds to start (loading files, connecting, preparing data). The splash screen:

- Tells the user the app is starting and not frozen.
- Shows progress so waiting feels shorter.
- Can show branding, version, and status.

### Components of a splash screen

- **Version number** — which version of the app is running.
- **Loading bar** — a progress bar showing how much of the startup is done.
- **Status bar / text** — a short message like "Loading resources..." or "Connecting...".

## Objects and properties

Almost anything in the program can be treated as an **object**, and each object has a few **properties** (its data).

For example, a drawn shape as an object:

```text
Circle
  - x        (position)
  - y        (position)
  - diameter (size)
  - color    (fill colour)
  - tag      (a label / id)
```

The idea is to pick 3 to 4 properties that describe the thing well enough for what the program needs to do with it.

## Multiple jobs, multiple threads, and cancelling a thread

If an application has to do several jobs at the same time (for example loading data while keeping the GUI responsive), each job can run on its **own thread**.

Sometimes we need to **cancel** a thread, for example if the user presses a cancel button or closes the window.

## Graceful cancellation

We should not just kill a thread suddenly, because it might be in the middle of something and leave data in a bad state.

Instead we do **graceful cancellation**:

1. Set a flag or send a signal that asks the thread to stop.
2. The thread checks this flag regularly during its work.
3. When it sees the signal, it finishes the current small step, cleans up, and then exits.

```java
volatile boolean cancelRequested = false;

// in the worker loop
while (!cancelRequested) {
    doOneStepOfWork();
}
// cleanup before the thread ends
```

This gives the task time to wrap up safely instead of stopping half way.
