## CI/CD

CI/CD is a way of automating the process of building, testing and delivering software.

**CI** stands for **Continuous Integration**. It means that developers regularly add and integrate their code into a shared repository. When new code is added, the project can automatically be built and tested to check whether the changes have caused any problems.

**CD** can mean **Continuous Delivery** or **Continuous Deployment**.

Continuous Delivery means that the application is automatically built, tested and kept ready for release. Continuous Deployment goes one step further and automatically releases the application to production.

So, in simple terms:

```text
CI = Regularly integrate, build and test code

Continuous Delivery = Automatically prepare code for release

Continuous Deployment = Automatically release code
```

The main idea is that instead of manually doing all these steps every time, the process can be automated.

## CI/CD and Maven

Maven can be used as part of a CI/CD pipeline because it provides standard commands for building and testing a Java project.

Some commands we can use are:

```text
mvn clean
mvn compile
mvn test
mvn package
```

For example, a CI system can run `mvn test` whenever new code is pushed. If a test fails, the problem can be identified before the code is merged or released.

The `pom.xml` file is important because it tells Maven about the project, its dependencies and the plugins required during the build process.

## JUnit

**JUnit** is a testing framework used for testing Java code.

Instead of manually checking whether a method gives the correct result, we can write **test code** that automatically checks it.

For example:

```java
@Test
public void testAddition() {
    assertEquals(5, add(2, 3));
}
```

Here, `@Test` tells JUnit that this is a test method and `assertEquals` checks whether the actual result is equal to the expected result.

This makes it easier to check that existing code still works after making changes.

## JUnit in pom.xml

JUnit needs to be added as a dependency in the Maven project. In the `pom.xml` we looked at, the testing dependency was:

```xml
<dependencies>
    <dependency>
        <groupId>junit</groupId>
        <artifactId>junit</artifactId>
        <version>4.11</version>
        <scope>test</scope>
    </dependency>
</dependencies>
```

The `<scope>test</scope>` means that JUnit is needed for testing but is not required as part of the main application.

The `pom.xml` also contained the Maven Surefire plugin:

```xml
<plugin>
    <artifactId>maven-surefire-plugin</artifactId>
    <version>2.22.1</version>
</plugin>
```

Surefire is used by Maven to run the tests during the test phase.

So when we run:

```text
mvn test
```

Maven can use the test dependencies and Surefire to find and execute the test code.

This is one reason Maven is useful in CI/CD because the same testing process can be run automatically on a server whenever new code is pushed.

## Headless Testing

**Headless testing** means running tests without needing a graphical user interface or physical display.

This is useful for CI/CD because tests are often run on remote servers where there may be no monitor or normal desktop environment.

For example, if an application contains GUI-related code, testing it in a headless environment means the testing process cannot depend on someone manually opening the GUI.

This makes automated testing easier to run on servers and helps ensure that the project can be tested without a person being present.
