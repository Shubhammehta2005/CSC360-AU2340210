## 1. Streaming vs Downloading

Both streaming and downloading transfer data from a remote source, but they differ in how the data is consumed and retained.

### Streaming

Streaming sends content progressively, allowing the user to begin consuming it before the complete resource arrives.

Examples include:
- Online video playback
- Internet radio
- Cloud gaming
- Remote desktop sessions
- Live camera feeds

Streaming can be **live** or **on demand**.

A player usually maintains a buffer. If incoming data becomes slower than playback, the buffer can empty and cause a pause. Adaptive bitrate systems can switch between quality levels depending on network conditions.

### Downloading

Downloading normally transfers a resource to local storage so it can be used later without another network transfer.

Examples:
- Software installers
- Photos
- Offline films
- Documents

### Main differences

| Aspect | Streaming | Downloading |
|---|---|---|
| Consumption | Starts before the entire resource arrives | Usually used after sufficient data is downloaded |
| Connection | Usually needed during playback | Mainly needed during transfer |
| Storage | Temporary buffer/cache | Local file |
| Repeated use | May require another transfer | Local copy can be reused |
| Quality | Can adapt to network conditions | Usually fixed by the downloaded file |
| Live content | Naturally supported | Cannot download a complete live resource before it exists |

### Data consumption

Neither method automatically uses more data. Transfer size depends on factors such as:

- Resolution and compression
- Amount of content consumed
- Quality adaptation
- Caching
- Repeated playback
- Protocol overhead

Streaming may avoid transferring content the user never watches. Downloading may be more efficient when the same file will be accessed repeatedly.

## 2. Server-Side Rendering vs Client-Side Rendering

Rendering describes where the application's page content is generated.

### Server-Side Rendering (SSR)

With SSR, the server creates the HTML and sends the rendered page to the browser. JavaScript can later hydrate the page to provide interactive behavior.

**Advantages**
- Useful content can appear quickly.
- Search engines can access rendered content more easily.
- Link previews can obtain page information directly.
- Some content remains visible even if JavaScript is delayed.
- Rendered responses may be cached by servers or CDNs.

**Limitations**
- Rendering increases server workload.
- Dynamic pages can increase response time.
- The page may appear before it becomes interactive.
- Hydration requires additional browser work.
- Personalized pages are harder to cache safely.

### Client-Side Rendering (CSR)

With CSR, the browser initially receives an HTML shell and JavaScript. The JavaScript then obtains data and constructs the interface.

CSR is commonly suitable for highly interactive applications such as dashboards, administration tools, and design applications.

**Advantages**
- Rich client-side interaction and state management
- Fast navigation after initial loading
- Less server-side HTML generation
- Application shells can be hosted as static assets
- Frontend and backend APIs can be separated clearly

**Limitations**
- Initial JavaScript download and execution can be expensive.
- The application depends more heavily on JavaScript.
- Search indexing and link previews may require additional support.

### Comparison

| Concern | SSR | CSR |
|---|---|---|
| Initial HTML | Usually contains page content | Often mainly an application shell |
| First display | Can show content earlier | Depends on JavaScript initialization |
| Server rendering | Higher | Lower |
| Later navigation | Depends on architecture | Often quick after startup |
| SEO | Generally straightforward | May need prerendering/crawler support |
| Interactivity | Begins after scripts/hydration | Begins after client initialization |

Modern applications may combine both approaches through hybrid rendering, static generation, client-side navigation, and selective hydration.

### Accessibility

Rendering strategy alone does not determine accessibility. Good accessibility requires:

- Semantic HTML
- Keyboard navigation
- Proper focus handling
- Meaningful labels
- Adequate contrast
- Correct handling of dynamic content
- Testing with assistive technologies

## 3. Image Storage Architecture

Image files are binary data and are commonly stored in object-storage systems such as Amazon S3. Application metadata can be maintained separately in a database.

### Common design

**Object storage contains:**
- Image bytes
- Object key/path

**Database contains metadata such as:**
- Image ID
- Filename
- MIME type
- Dimensions
- File size
- Owner or related record
- Upload time
- Access permissions
- Checksum/hash

This separation allows the application to query metadata efficiently while object storage handles large binary files.

### Why object storage is useful

Object-storage services are designed for large-scale file storage and commonly provide:

- High durability
- Scalability
- Access control
- Encryption
- Lifecycle policies
- Versioning
- CDN integration

Private images can be delivered through time-limited signed URLs instead of exposing the objects publicly.

### Can databases store images?

Yes. Relational databases can use binary/BLOB columns, and some document databases support binary values.

Direct database storage can make sense when:
- Files are small
- Transactional consistency is important
- The number of files is relatively limited
- A single-store backup/access model is desirable

For large media systems, separating image storage from metadata is often more practical. The appropriate architecture depends on file size, traffic, security, consistency, backup requirements, and cost.

## 4. Exam Revision Summary

- **Streaming** delivers data progressively; **downloading** normally creates a reusable local copy.
- Streaming may use buffering and adaptive quality to handle changing network conditions.
- Data usage depends on content quality, duration, caching, and repeated access.
- **SSR** generates page content on the server, while **CSR** builds much of the interface in the browser.
- SSR can help with initial content visibility and indexing but requires additional server rendering and hydration work.
- CSR is useful for interactive applications but can have a larger initial JavaScript cost.
- Accessibility depends on semantic structure, keyboard support, focus management, labels, contrast, and dynamic-update handling.
- A common image architecture stores binary files in object storage and related metadata in a database.
- Database-based image storage is possible, especially for smaller or tightly transactional workloads.
