## Understanding the Binary Tree Model

Before working further on the visualizer, I also understood how the actual binary tree is represented in code.

There are two important classes in the model package:

```java
public class BinaryTree<T> {
    private TreeNode<T> root;
}
```

and:

```java
public class TreeNode<T> {
    private T data;
    private TreeNode<T> left;
    private TreeNode<T> right;
}
```

`BinaryTree` represents the complete tree, while `TreeNode` represents an individual node inside that tree.

The `BinaryTree` mainly keeps track of the root node:

```java
private TreeNode<T> root;
```

It also provides methods to get and change the root:

```java
public TreeNode<T> getRoot() {
    return root;
}

public void setRoot(TreeNode<T> root) {
    this.root = root;
}
```

It also has simple methods to check whether the tree is empty and to clear it:

```java
public boolean isEmpty() {
    return root == null;
}

public void clear() {
    this.root = null;
}
```

The `TreeNode` class contains the actual data and references to its two possible children:

```java
private T data;
private TreeNode<T> left;
private TreeNode<T> right;
```

So a node can be visualized as:

```text
        Node
       /    \
   left     right
```

The node uses getters and setters to access or modify these values:

```java
public T getData() {
    return data;
}

public TreeNode<T> getLeft() {
    return left;
}

public void setLeft(TreeNode<T> left) {
    this.left = left;
}

public TreeNode<T> getRight() {
    return right;
}

public void setRight(TreeNode<T> right) {
    this.right = right;
}
```

I also learned about the `isLeaf()` method:

```java
public boolean isLeaf() {
    return left == null && right == null;
}
```

A leaf is a node that does not have either a left or right child.

Both classes use **generics** (`<T>`), which means the tree can store different types of data without having to create a separate class for each data type.

For example:

```java
BinaryTree<Integer>
BinaryTree<String>
```

This separation makes the model reusable and keeps the actual data structure independent from the JavaFX graphical representation.

## Connecting Data Structures with Graphics

The main goal of our project is to take an abstract data structure and represent it visually.

In our case, we are working with **Level-Order Binary Trees** and **Binary Search Trees (BSTs)**.

The basic flow is:

```text
Input Data
    ↓
Build Data Structure
    ↓
Calculate Node Positions
    ↓
Render Graphically
    ↓
Interactive Visualization
```

This helped me understand that a data structure does not have to remain only as code. It can be represented visually so that its structure becomes easier to understand and interact with.

## Mathematical Modeling for Tree Layout

One of the more difficult parts of the project is deciding where each node should appear on the screen.

For every node, we need to calculate an `(x, y)` position.

For example:

```text
          10
        /    \
       5      15
      / \    / \
     2   7  12  20
```

As the tree becomes deeper, simply using fixed positions can cause nodes and branches to overlap.

Therefore, our `TreeLayoutCalculator` uses the depth and spacing of the tree to calculate suitable positions.

The main idea is that nodes at different levels need different amounts of horizontal space so that the branches remain visible and do not overlap.

This showed me how mathematical calculations can be important even in something that looks like a simple graphical interface.

## Clean Architecture

Another important topic was **separation of concerns**.

Instead of putting all the logic in one class, different parts of the application are responsible for different things.

For example:

```text
TreeNode / BinaryTree
        ↓
   Data Structure

TreeLayoutCalculator
        ↓
   Node Positions

TreeCanvasPane
        ↓
    Rendering

Control Panel
        ↓
   User Interaction
```

The `TreeNode` and `BinaryTree` classes deal with the actual data structure, while the rendering classes deal with displaying it.

This makes the project easier to understand, modify and maintain because changing the graphical representation does not require changing the underlying tree structure.

## JavaFX Events and Edge Cases

We also worked with JavaFX events and graphical interactions such as **panning and zooming**.

These features require the application to respond to mouse and other UI events while keeping the rendering smooth.

Another issue is what happens when the user enters more nodes than can reasonably fit inside the available window.

Instead of allowing the tree to grow indefinitely and cause rendering problems, the application calculates the maximum number of nodes that can fit and trims the input when necessary.

For example:

```text
Input → Check Available Space → Calculate Maximum Nodes
                         ↓
              Trim if Necessary
                         ↓
                  Render Tree
```

This makes the application more stable and gives the user a better experience.

Overall, today's class helped me understand that building a visualizer involves much more than simply drawing nodes on the screen. We need to combine data structures, mathematical calculations, software architecture and UI event handling. I also understood why separating different responsibilities in the code is important for keeping the project scalable and maintainable.
